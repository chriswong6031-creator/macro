## CI handoff is terminal (STANDING — HIGHEST PRECEDENCE)

**"System done" and "worker done" are different states, and on any conflict this section outranks every other completion rule in this file.** SYSTEM done is still the whole chain below. WORKER done is earlier — and a worker still breathing past it is spending frontier context (§Context economy: cost = CONTEXT × TURNS) re-asking a question `merge-on-green` already re-derives from GitHub's live state every 10 min, on the same 5,000/hr REST bucket `ship_loop_guard.py` fails CLOSED without.

A worker task is COMPLETE and MUST terminate once all five hold: (1) the intended changes are committed and pushed; (2) the remote PR head equals the expected local HEAD; (3) the PR carries `merge-on-green`; (4) at least one non-spurious check has started, or a no-CI proof exists; and (5) no concluded genuine-red check exists. The worker then runs `python3 scripts/ci_handoff.py` — the universal CLI over `scripts/ci_handoff_contract.py`, the SAME classifier `.claude/hooks/ship_loop_guard.py` holds, so hook and CLI can never disagree about whether you may leave — emits the `CI_HANDOFF=` receipt line it prints, gives its final response, and terminates. Exit 0 is the release; exits 2–7 each NAME the condition that failed (2 red, 3 unproven, 4 checkout/head, 5 no armed PR, 6 sink, 7 infra), so a refusal is a work item, never a reason to wait.

**After `CI_HANDOFF`, waiting, polling, rerunning, merging, observing the deployment, and continuing the next phase in the same session are FORBIDDEN.** The external controller owns those states. Nothing in the delivery contract is weakened by this: the sweeper still merges, the render lane still bakes, the VPS still pulls its 3-min main — you are simply not the one sitting there watching them. Condition (4) is why an unproven head still blocks: an absence of red is not a pass (#4779), and releasing on a head nothing proves ORPHANS the work, because the sweeper will refuse it too.

## Context economy (STANDING — Fable burn is CONTEXT × TURNS, not thinking; measured 2026-08-06)

**The expensive thing is re-reading context, not reasoning.** Week of 2026-07-30→08-06, measured across 3,043 local transcripts: Fable = 1,902M weighted units (26% of all model burn; Opus was 62%). Of that Fable burn, **62% was cache READS, 21% cache writes, and only 17% output.** Cache reads are the *discount* (0.1× fresh input) — never try to "avoid caching", the alternative is paying 10× for the same tokens. What costs money is the product **context size × turn count**.

Per-turn cost floor = `0.1 × context`. A turn at 150k context costs ~15k units before the model does anything; at 800k it costs ~80k. The top session that week (`bf6ce626`, 220M = 11.6% of the entire week's Fable) ran **3,539 turns at a median 419k context, max 879k, over 43h and 16 git branches**. Its turns at ≥400k context were 52% of turns but **67% of its burn**; the 700k+ band cost 92k units/turn, **3× a turn at 100–200k**. Those same 3,539 turns held at 150k would have cost ~53M instead of 196M.

**Riding context up to auto-compaction is the most expensive possible pattern.** Auto-compaction fires near the ceiling, so every turn on the approach is billed at the ceiling rate. There is no configurable compaction threshold, and the model **cannot compact itself on demand** — so the only real controls are the three below.

- **Delegate execution; the orchestrator adjudicates.** Measured: 76% of Fable's main-loop tool calls were `Bash`/`Edit`/`Read`/`Write` and delegation was **2.6%** of tool calls — Fable was grinding, not orchestrating. A subagent's context is **discarded on return** (only its report lands), so delegating keeps tool output out of the orchestrator permanently. Route per §Model routing: `builder` (opus) builds, `reviewer` (opus) reviews, `Explore`/`general-purpose` (sonnet) censuses.
- **Budget what enters context.** A tool result of size S landing at turn N is re-read on every one of the remaining turns. A 20k-token Bash dump at turn 500 of a 3,539-turn session costs ~6.1M weighted units downstream. Prefer targeted `grep`/line-ranged `Read` over whole-file reads; cap command output (`head`, `--limit`, `--jq`); never pull browser screenshots or full page dumps into an orchestrator — those belong in a subagent.
- **One session = one task boundary.** When the work item is committed/merged, write the handoff and STOP. A long program does NOT need a long session — it needs durable state on disk, which is already the house pattern (125 `research/` masterplans and the live `research/*_CONTINUATION_HANDOFF_<date>.md` convention). Run long programs as a **chain of short sessions** over that doc, one wave per session. Target: keep an orchestrator under ~200k; past ~250k mid-program, checkpoint to a handoff and let the operator `/clear` rather than grinding to the ceiling.

**Explicit non-goal — do NOT save tokens by making Fable think less.** Output is only 17% of Fable burn, so cutting effort/reasoning degrades the model for at most a sixth of the cost. Keep `effort` where the task needs it. The savings are in *where work happens* and *how big the context is*, never in the quality of the thinking. Modelled on the measured top-12 sessions: delegating execution (−40% turns) plus holding context near 150k cuts those sessions ~66% — about **−28% of the week's Fable burn** — with the same work done.

## Spawn-handoff law (STANDING — quality does not travel by pointer; onboarding postmortem 2026-07-23)

A spawned/chipped session starts with ONLY its prompt + the target repo's CLAUDE/AGENTS file. The onboarding flow shipped broken-and-ugly despite a correct masterplan AND correct model tiers (Fable loop + Opus builders): reference shots existed only as prose, acceptance gates sat at §6/§7 of a referenced doc, the target repo's agent laws were 5 lines of Next.js warnings, and the PR self-merged with no visual artifact. 2. **Reference images = committed files** (`mockups/refs/<program>/`) with paths in the prompt. Never hand off a look in prose — the session cannot see your screenshots.
