## 7. F11 Thesis Object architecture freeze

### 7.1 Product host ruling

F11 is a first-class mode inside Terminal's authenticated `/analysis` workspace. It is not a separate application and not another company-only finance tab.

Recommended stable deep link:

`/analysis?view=theses&thesis=<uuid>`

A symbol may be present as context but is not required, because theses can address securities, issuers, themes, macro topics, or user-defined subjects.

### 7.2 Storage and tenancy ruling

F11 private state belongs in Terminal/Supabase User Plane with owner-only row-level security.

Version 1 is **user-scoped**. It must not invent a misleading `workspace_id` before real team tenancy and membership rules exist. Sharing, collaborative editing, organization roles, and external publication are separate future architecture decisions.

Macro Git or public data must never become the private thesis database.

### 7.3 Core schema

#### `theses`

Mutable head/index row only:

- `id UUID`;
- `user_id UUID REFERENCES auth.users`;
- `current_version_id UUID`;
- server-created `created_at` and `updated_at` UTC;
- owner-only RLS.

#### `thesis_versions`

Immutable snapshots:

- `id UUID`;
- `thesis_id UUID`;
- `user_id UUID`;
- monotonic `version_number`;
- `amended_from_version_id UUID NULL`;
- `event_type`: `created | revised | archived | reopened | invalidated`;
- `status`: `active | archived | invalidated`;
- `title`;
- `claim`;
- `rationale`;
- `horizon`;
- optional user-entered `direction` and `confidence`, explicitly descriptive and non-authoritative;
- canonical server `recorded_at` UTC;
- optional explicit user `effective_as_of`;
- `client_request_id` unique per user/thesis for idempotency.

No UPDATE or DELETE of version content is allowed through product paths. Archive, reopen, and invalidate create new versions.

#### Later version-scoped link tables

- `thesis_version_subjects`;
- `thesis_evidence_links`;
- `thesis_condition_links`.

Links are immutable with the version snapshot. A later revision creates new links rather than rewriting the historical version.

### 7.4 Atomic mutation contract

Implement server-side transactional functions or equivalent trusted server operations:

- `create_thesis_v1(...)`;
- `append_thesis_version_v1(expected_current_version_id, client_request_id, ...)`.

The append path must:

1. authenticate the caller server-side;
2. lock or compare the current thesis head;
3. reject a stale expected head with typed `THESIS_VERSION_CONFLICT` and return the current head;
4. insert the immutable version;
5. update `theses.current_version_id` in the same transaction;
6. make a repeated `client_request_id` idempotent;
7. never accept a browser-supplied `user_id` as authority.

### 7.5 Subject identity contract

`thesis_version_subjects` references owner-native entities; it does not mint a new entity plane.

Required shape:

- `subject_type`: `security | issuer | theme | macro_topic | custom`;
- `owner`;
- `owner_id`;
- display label frozen for the historical version;
- resolution state, resolution time, and owner/source version.

External subjects must be owner-resolved. Unresolved identity remains visible and blocks claims that require canonical linkage. `custom` is explicitly user-defined and carries no external identity promise.

The first product slice may support canonical security context plus `custom`/general macro thesis. Broader owner coverage follows without changing the core object.

### 7.6 Evidence contract

Evidence links point to Evidence Foundation `reference_id` or an owner-native source identifier. They never copy source bodies.

The UI must preserve:

- the reference as linked at that thesis version;
- current correction/retraction/rights/missingness state resolved from the owner;
- exact source, publication, event, acquisition, and availability clocks where available;
- explicit unavailable or rights-restricted states.

A historical thesis version remains immutable when evidence changes. A user can create a new revision that responds to the correction.

### 7.7 Conditions and notification contract

Reuse the deterministic semantics of `engine/falsifier_tripwires.py`:

- `ARMED`;
- `FIRED`;
- `RECOVERED`;
- `DEGRADED`.

A fired transition remains sticky until the source/version contract explicitly changes; it must not silently auto-unfire. Missing sources yield `DEGRADED`, never `false`, `zero`, or an inferred pass.

User-facing language should be:

- change condition;
- at risk;
- failed;
- recovered;
- data unavailable.

Do not expose “falsifier” as the default customer vocabulary.

Condition definitions and user result state belong in the User Plane. Deterministic evaluation code remains in the canonical Macro owner. Delivery consumes transitions through the existing F08 notification path. No second cron, queue, or delivery engine is permitted.

### 7.8 Brain and model authority

Later Brain integration binds context through existing thread metadata, such as `active_thesis_id` and `active_thesis_version_id`.

Models may:

- draft a thesis;
- summarize evidence;
- propose subjects, references, conditions, or revisions;
- explain changes;
- propose a reopen-with-delta draft.

Models may not silently publish a version, resolve identity, determine source clocks, override corrections, evaluate deterministic conditions, deduplicate delivery, rank opportunities, gate trades, size positions, or originate trade authority.

A model proposal remains a Brain message or draft until an explicit user confirmation creates a canonical immutable version.

### 7.9 RMS composition ruling

Coverage, Ideas, Notes, Theses, Catalysts, Risks, and Reviews are views, filters, or compositions over canonical user objects. They are not seven new stores.

The first canonical object is the Thesis. Notes may remain existing notes until a later explicit unification ruling. A “Research Management System” is the experience layer over these owners, not a database brand.

### 7.10 Failure and privacy states

The product must visibly handle:

- empty thesis list;
- loading and slow network;
- offline or failed save;
- stale concurrent edit conflict;
- unauthorized or missing deep link;
- unresolved subject identity;
- missing/retracted/stale/rights-restricted evidence;
- condition source degradation;
- archived or invalidated thesis;
- partial downstream service availability.

Unauthorized access returns not-found semantics without confirming another user's object exists. Private API responses use `Cache-Control: private, no-store` and `Vary: Authorization` where applicable. No service-role credential may reach browser code.
