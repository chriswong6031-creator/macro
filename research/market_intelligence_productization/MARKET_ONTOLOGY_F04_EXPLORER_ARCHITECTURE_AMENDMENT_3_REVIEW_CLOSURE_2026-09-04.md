## 3. Product archetype and the two theme art directions

The route's canonical design-system archetype is `instrument_analyzer`, C-signal subtype.
The selected instrument is the **typed path**, and its primary job is: what is this path,
what has changed, what is supported, and what would invalidate it? The decision header maps
to the Trace Narrative; the dated lifecycle rail maps to ordered hop state; evidence,
invalidators, risk, and provenance remain progressively disclosed. This does not turn a
historical rate into a decision score.

### Dark treatment — command-center instrument calm

- graphite canvas with luminance depth and restrained bloom only around genuinely live state;
- typed hop states earn contrast through hierarchy, not neon saturation;
- observed, historical, hypothesis, and unavailable remain visually distinct;
- dormant or contradictory paths remain calm and legible and never glow as active;
- graph/path depth is conveyed by governed surfaces and hairlines, not a parallel palette.

### Light treatment — research workspace

- cool canvas with white material, disciplined hairlines, whitespace, and controlled shadow;
- evidence and provenance read like an institutional research sheet rather than a recolored
  dark canvas;
- active/dormant/unavailable hierarchy is rebuilt through ink, border, surface, and spacing;
- no glow-dependent distinction, low-contrast pastel state, or mechanical token substitution.

The information architecture, semantics, ordering, actions, clocks, density, and interaction
behavior are identical across themes; material depth intentionally differs. Required evidence
is dark/light × EN/ZH × desktop 1440/mobile 390, including stale, locked, dormant,
contradictory, regime-unavailable, and method-unavailable states. A missing light treatment
or evidence cell is `PARTIAL/BLOCKED`, never `PASS`.

## 4. Request-time freshness and deployed-checkout lag

X1's preferred API composes at request time from the exact owner artifacts available in the
**deployed checkout**. Freshness is a content identity and deployment-state question, not a
nightly job-order question.

For every response:

1. resolve the exact deployed owner file/path or owner-native generation;
2. read immutable input bytes and generation/clock identities;
3. derive `source_manifest_hash` from all exact input bytes/generations plus composer method
   version;
4. bind every material node, edge, and path to its owner generation;
5. validate the pure projection and return it with visible owner as-of and build clocks;
6. compare the deployed checkout/build identity with the current release/source identity;
7. if source contains a newer owner generation that deployment has not pulled or deployed,
   return a typed `DEPLOYED_CHECKOUT_LAG` / `DEPLOY_PULL_LAG` degradation with source and
   deployed identities and measured age; never call the response current;
8. if an owner artifact itself is stale under owner law, return `SOURCE_STALE` separately.

`source_manifest_hash` proves which bytes were composed; it does not prove that deployment
contains the newest repository bytes. A request-time response needs no Ontology snapshot job
after TXI/rates. A later private precompute may have an owner-specific ordering contract only
after a separate accepted transport/owner ruling.

## 6. Denominator honesty, regimes, and visible clocks

### 6.1 Two different `N` values must never be conflated

The current hop calibration in `engine/transmission_calibration.py::_confirm_flags` counts
upstream **rising-edge episodes**. Therefore hop `n` and each regime-cell `n` are episode N:
one false-to-true activation per upstream episode, with right-censored forward windows
dropped.

The current `cohort_event_study`, by contrast, samples every bar on which the terminal node
is true. Its `n` is a **per-bar cohort row count**. Adjacent rows have overlapping 21- or
63-session forward outcomes and are not independent episodes.

The UI and API must label these separately:

```text
hop_episode_n
cohort_bar_n
cohort_effective_n
cohort_overlap_policy
cohort_interval
cohort_span
cohort_concentration
```

The present owner artifact emits only `cohort_bar_n`. Until the owner emits a defensible
effective N, overlap/autocorrelation treatment, interval, event span, and temporal/episode
concentration, the other fields are typed `UNAVAILABLE_NOT_EMITTED_BY_OWNER`; the terminal
cohort distribution remains descriptive and cannot support confidence, promotion, or an
independent-sample claim. F04 may not approximate effective N from the horizon.

### 6.2 Regime availability

Where a hop's `regime_split` is unavailable, display `REGIME_UNAVAILABLE` plus the owner's
reason and pooled episode N. Where historical regime cells exist but the response cannot
resolve the current tape into the declared `regime_scheme` at the snapshot's knowledge
cutoff, display `CURRENT_REGIME_UNAVAILABLE` and do not select a cell. Never treat the
largest cell, newest label, or a blank as the current regime.

### 6.3 As-of and build clocks

Every product-visible owner panel and evidence drilldown shows both clocks. The architecture
reference values are historical evidence, not runtime constants:

| Artifact at PR #6820 archaeology | Owner as-of | Built |

| `data/transmission/chain_calibration.json` | `2026-08-21` | `2026-08-22 16:34 UTC` |

The workspace toolbar shows the selected snapshot/source-manifest clock summary; inspectors
