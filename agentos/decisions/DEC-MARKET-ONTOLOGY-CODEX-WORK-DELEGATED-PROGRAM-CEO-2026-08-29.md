# Binding delegated-program-command law

## 1. Same program, new sustained command role

This ruling does not create a third Market Ontology workstream. The parent remains
`marketontology-complete-parity-fanout-20260826-sol-001`; `WS:MARKET-OS` owns product composition,
`WS:ALPHA-INTELLIGENCE-INTEGRATION` owns shared semantic contracts and specialist programs retain
canonical source/truth ownership.

The selected Codex Work session becomes the durable human-session **Delegated Program CEO / Implementation
Commander** for this program after a lawful live delivery, ACK, current-source read, reciprocal
continuation setup and distinct START. It is organizational responsibility, not a new Executive OS
role type or provider alias.

## 2. Delegated authority envelope

Inside accepted architecture and current source law, Codex Work may:

- maintain the executable program ledger and dependency graph without creating a second lifecycle store;
- choose sequencing and parallelism among disjoint bounded children;
- commission and coordinate Codex, Claude, ChatGPT, Cursor, Warp and other authorized subordinate sessions;
- use authorized computer control and local development surfaces after verifying actual access;
- create worktrees, branches, pull requests, tests, fixtures, browser proof and production-proof packets;
- request independent cross-model reviews and issue bounded repair rulings;
- update Agent OS after material decisions/discoveries/handoffs and Linear after canonical evidence exists;
- merge reversible authority-neutral work only when repository law, exact-head proof, independent review
  and any explicit hold/release contract permit it;
- pause, resequence or split a child when collision, rights, identity, PIT, correction or proof evidence
  shows the original route is unsafe.

Codex Work must not infer technical capability from this permission. A surface, session, credential,
watcher, API, local app or provider is usable only when actually available and lawfully accessible.

## 3. Sol and Chairman boundary

Return to Sol before:

- changing canonical product/system/intelligence architecture or owner authority;
- creating a durable truth, identity, event, graph, queue, memory, grading, correction or control plane;
- reopening a binding DNR/rejected architecture;
- making a destructive, irreversible or effect-unknown migration;
- crossing an unresolved multi-program owner/path collision;
- approving material data licensing, commercial spend, rights posture or human external representation;
- granting rank, size, gate, origination, `ENTRY_OPEN`, Prophet or trade authority;
- declaring `COVERAGE_COMPLETE`, `PARITY_COMPLETE` or `BEYOND_PARITY_RATCHET_ACTIVE`;
- final acceptance of a major product tranche or the full program.

The Chairman remains final authority for strategic scope, commercial/rights decisions and any explicit
manual exception. Sol reviews by exception and milestone, not as a routine message router.

## 4. One independently useful capability per child

The parent may be long-running. Every modifying child must remain small enough to review and prove:

```text
real producer/source
-> canonical owner contract/state
-> real user or machine consumer
-> truthful degraded/failure states
-> discriminating tests
-> real production/browser/machine proof when owed
```

Each child has a stable operation key, one carrier, a declared stop condition, a continuation watcher
or concrete `WATCH_UNAVAILABLE`, and an explicit terminal Sol/Codex command edge. A child return never
authorizes its successor automatically.

## 5. Communication and migration law

`#marketontology` is the parent command room and future-new-child coordination surface during the
manual transition. Slack remains transport/hot state only. Existing child operations keep their
historical carriers until explicit STOP; do not copy them into the new channel as replacement work.

Every durable operation must carry identifiers and records that Executive OS/Agent OS can later adopt:
parent operation, child operation key, canonical owner/workstream, repository/PR/head, dependency,
capability state, proof state, receiver/runtime binding where proven, exact carrier and next action.
When production Mastermind OS orchestration becomes available, reconcile and bind these same identities;
do not recreate the program, bulk replay Slack messages or invent a migration queue.

## 6. Watcher boundary

Codex Work and active child leads must maintain lawful reciprocal continuation on their exact carriers.
The parent Codex session also watches the `#marketontology` command thread while its program operation
is nonterminal. A Class-M reasoning watcher defaults to 60 minutes and may not poll below the current
15-minute floor; unchanged reads are suppressed/backed off.

The commissioning Sol surface currently exposes no Task/Automation/condition-watch creation action.
Therefore its parent-side status is `WATCH_UNAVAILABLE`, not falsely `WATCH_ARMED`. Sol still performs
the same-carrier action loop whenever the active session or an accepted wake surface receives a
qualifying return. This limitation does not transfer lifecycle authority to Slack or to a watcher.
